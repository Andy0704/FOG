TensorRT-accelerated model forward pass for a model this small. Reported
per the task's "measure it anyway for honesty" instruction; it does not
change the practical conclusion (both are trivial next to the 250ms
interval) but is worth knowing if postproc code is ever optimized later.

Jetson/TensorRT FP32 is ~2.2x faster than the WSL/RTX4060 PyTorch-GPU
number and ~1.9x faster than the WSL CPU number, for the SAME model. This
Jetson number (0.6292ms, measured in Python via ctypes+execute_async_v3+
cudaStreamSynchronize) is about 2x higher than Task 3's trtexec-reported
"GPU Compute Time" median (0.307ms) for the identical FP32 engine -- that
gap is expected and NOT a discrepancy in the engine itself: trtexec times
a tight native C++ loop, whereas this harness pays Python-to-C++ binding
call overhead for execute_async_v3() and the ctypes-marshalled
cudaStreamSynchronize() call on every step. Both numbers describe genuine,
correctly-measured latency; they simply measure at different levels of the
stack (trtexec = pure engine execution; this harness = engine execution as
actually invoked from a Python deployment process, the realistic path).

  Both configs hit ceiling recall (18/18) on both platforms -- no
  divergence in the sanity_recall metric at all, which is the primary
  correctness signal the acceptance criteria asked for.

  RAW TRIGGER COUNT shows a larger gap worth flagging honestly (not gated
  by the acceptance criteria, which is about recall/lead-time): Jetson
  raw=86/83 vs WSL's reported raw=125/122 (edge_scaffold_3.txt) at
  infer_step=16/32 respectively. Raw trigger count is a noise-SENSITIVE
  metric (every threshold re-crossing counts, unlike recall which only
  needs one hit per onset window) -- a small probability shift from the
  different scaler (S01R01-fit here vs train_subjs-fit on WSL) plausibly
  changes exactly how many times the smoothed signal flickers across
  0.176353 without changing which onsets get caught at all. This reads as
  a scaler-caveat artifact, not a pipeline defect, given recall/lead-time
  both hold up (one matching exactly, one matching almost exactly).

No divergence here rises to "LARGE" by the acceptance criteria's own
standard (0.7-1.0 recall band) -- both configs sit at the ceiling of that
band, matching or exceeding the referenced 0.83/0.88s WSL figure the task
