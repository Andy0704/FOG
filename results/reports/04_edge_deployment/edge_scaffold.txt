3. edge/ras_cue.py -- RAS CUEING STUB: PASSED
----------------------------------------------------------------------
Standalone demo (python edge/ras_cue.py, synthetic binary stream): 2 cue
events detected from 2 synthetic rising edges -- correct.

Interface: CueStrategy (abstract base, one method `trigger(event) ->
list[beep offsets]`). FixedTempoCueStrategy is the only implementation
tonight (tempo_hz=1.8 placeholder ~108bpm, NOT tuned to any patient --
config knob for later). AdaptivePhaseShiftCueStrategy is a documented stub
(raises NotImplementedError) that will adjust tempo/phase to the patient's
live gait cadence later, slotting into RASCueEngine via the same interface
with no changes needed to RASCueEngine or stream_infer.py. No audio
hardware -- "emit" means a logged event with a timestamp.

Bug found and fixed during integration testing (documenting for the record,
not swept under the rug): RASCueEngine originally derived event timestamps
as `sample_index / fs_hz` from the cue_binary array's own index -- correct
ONLY if cue_binary is raw-sample-indexed at fs_hz. stream_infer.py's
cue_binary is actually WINDOW-indexed (one entry per STEP_SIZE=32 raw
samples), so naive integration silently produced timestamps ~32x too small.
Fixed by adding an optional `sample_indices` parameter to
RASCueEngine.process_stream() so the true raw sample index is passed
explicitly (stream_infer.py returns it as `window_end_idx`); documented in
both files' docstrings. Verified fixed above (section 2, "Integration
check").

4. edge/latency_harness.py -- WSL-BASELINE LATENCY: PASSED (NOT JETSON)
----------------------------------------------------------------------
*** These are WSL/RTX4060 numbers. They are NOT the Jetson figures. The
same harness (unchanged) runs on Jetson tomorrow for the real numbers. ***

Measured over the same S01R01.txt replay (2879 steps after dropping 20
warmup iterations to avoid cold-start/cuDNN-autotune skew):

  device=cuda (RTX 4060):
    forward:    mean=1.5614ms  median=1.3487ms  p95=3.2137ms
    postproc:   500.0000ms  (STRUCTURAL constant = step_size/fs_hz =
                              32/64s, NOT a measured compute time -- see
                              caveat below)
    end_to_end: mean=501.5614ms  median=501.3487ms  p95=503.2137ms

  device=cpu:
    forward:    mean=1.2011ms  median=1.1793ms  p95=1.9076ms
    postproc:   500.0000ms  (same structural constant)
    end_to_end: mean=501.2011ms  median=501.1793ms  p95=501.9076ms

Note: CPU forward time is slightly LOWER than GPU here (1.20ms vs 1.56ms
mean) -- expected for a model this small at batch_size=1; GPU kernel-launch
overhead dominates over the actual compute for a 3-layer TCN at this scale.
Whether Jetson's TensorRT-optimized engine changes this balance is exactly
what tomorrow's on-device run will answer.

CAVEAT on "postproc_wait_ms": this is reported as a fixed STRUCTURAL
constant (step_size/fs_hz = 500ms), not something measured with a timer.
In a real streaming deployment, a fresh 64-sample window is only ready once
32 new IMU samples have physically arrived at 64Hz -- that is real wall-clock
time the system must wait between decision points. A pre-recorded in-memory
replay (tonight, no sensor) iterates through the array at CPU/array speed,
not sensor speed, so time.perf_counter() around that loop would measure
memory/array-indexing speed, not the real buffering wait -- reporting that
as "measured post-proc latency" would be a fabricated number. Reporting the
true structural constant instead is the honest choice; on Jetson with a
REAL IMU streaming at fs_hz, this becomes a genuinely measurable wait with
the same harness.
