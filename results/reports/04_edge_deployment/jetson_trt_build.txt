4. FLAG: FP16 speedup < 1.5x (in fact <1.0x -- no speedup at all)
----------------------------------------------------------------------
This model is extremely small (TCN with 32/64/128 channels, kernel size
<=5, window=64, batch=1) -- both FP32 and FP16 GPU Compute times land in
the same ~0.30-0.32 ms band, and total inference work per query is tiny
relative to fixed per-kernel launch overhead. Evidence this is a "too
small to benefit from FP16" situation rather than an unsupported-op
fallback:
  - trtexec reports "Precision: FP32+FP16" for the --fp16 build, i.e. it
    was ALLOWED to use FP16 kernels wherever beneficial, and its own
    autotuner (profiled per-tactic during the build, verbose log) still
    picked FP32-named conv tactics as fastest/competitive for these tiny
    channel counts -- not a case of an op TensorRT refuses to run in FP16.
  - Input/output tensor format is reported as "fp32:CHW" for both builds
    (expected: the ONNX graph's I/O dtype is float32 and no
    --inputIOFormats/--outputIOFormats=fp16 flag was passed in this task's
    trtexec commands, so I/O casts were never requested either way).
  - The 71% (not ~50%) engine-size ratio confirms a real mix of FP32 and
    FP16 weights, not a pure-FP16 engine that simply failed to speed up.
Conclusion: this is consistent with kernel-launch-overhead-bound latency
on a very small network, not a BatchNorm/op-specific FP16 incompatibility.
No corrective action taken in this task (Task 3 is build-only); worth
revisiting in Task 5's latency harness with repeated/batched queries to
see if the picture changes under sustained load, and worth noting for the
write-up that "FP16 is not automatically a win for very small edge models."
